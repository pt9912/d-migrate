# `include_comments` — den DDL-Header-Kommentar abschaltbar machen

> **Status:** Draft mit Scope (2026-09-13). Teil von
> [`open/ddl-config-block-unimplemented.md`](../open/ddl-config-block-unimplemented.md).

## Ziel

`ddl.include_comments: true|false` steuert, ob `schema generate` den
beschreibenden Header-Kommentar an den Anfang der erzeugten DDL setzt —
Vorrang **CLI-explizit > Config > Default** (Default `true`, heutiges
Verhalten unverändert), wie bei `--partition-storage`.

## Was der Schlüssel tatsächlich meint (gemessen)

Die Spec-Zeile trägt den Kommentar `# Header-Kommentar in DDL` — **nicht**
SQL-`COMMENT ON TABLE/COLUMN`. `TableDefinition`/`ColumnDefinition` tragen
heute kein `comment`-Feld; ein SQL-Kommentar-Feature wäre eine
Modellerweiterung samt Reverse-Unterstützung je Dialekt, ein deutlich
größerer Schnitt, den dieses Ticket **nicht** meint.

Gemeint ist der Block, den jeder erzeugte Lauf an den Anfang setzt:

```
-- Generated by d-migrate 1.5.0-SNAPSHOT
-- Source: neutral schema v1.0.0 "..."
-- Target: postgresql | Generated: 2026-09-13T...
```

Er entsteht an **einer** Stelle für alle fünf Dialekte:
`AbstractDdlGenerator.generateHeader()`
([`AbstractDdlGenerator.kt`](../../../adapters/driven/driver-common/src/main/kotlin/dev/dmigrate/driver/AbstractDdlGenerator.kt)),
aufgerufen von genau einer Zeile in `generate()`. Kein
Fähigkeits-Prerequisite fehlt — der Fall unterscheidet sich damit von den
beiden anderen Restpunkten dieses Trackers.

## Die offene Design-Frage: dreiwertige Boolean-Präzedenz

Die bestehenden Config-Schlüssel mit CLI-Gegenstück sind alle `String?`
(`mysqlNamedSequences`, `mssqlHashPartitions`, `partitionStorage`) — `null`
heißt dort natürlich „nicht gesetzt". Ein Boolean-Flag über Clikt
(`.flag()`) liefert dagegen immer `Boolean`, nie `Boolean?`: es gibt heute
**kein Vorbild** im Repo für „CLI-Flag explizit gesetzt vs. Default
übernommen" bei einem Boolean.

Zwei Wege, vor dem Bauen zu entscheiden:

1. **Paar-Flag mit Tri-State-Erkennung** — `--include-comments`/
   `--no-include-comments`, dahinter ein `Boolean?`, der nur bei
   tatsächlichem Aufruf eines der beiden Flags gesetzt wird (Clikt:
   `.flag(default = null)` ist nicht eingebaut, bräuchte einen eigenen
   `convert()`/zwei Options mit `eagerOption`-artiger Auswertung).
2. **Nur Config, kein CLI-Flag** — `include_comments` ist eine
   Ziel-Beschreibung (wie `mysql.engine`), kein Aufruf-Parameter; wer es
   abschalten will, tut das in der Konfigurationsdatei. Kein
   Präzedenz-Problem, weil es keine zweite Quelle gibt.

Tendenz: Weg 2. Ein Header-Kommentar ist wie `partition_storage` eine
Eigenschaft der Zielbeschreibung, kein Aufruf-Parameter, der von Lauf zu
Lauf wechselt — und es spart eine Tri-State-Lösung, die sonst als erstes
Vorbild für alle künftigen Boolean-Config-Schlüssel gälte.

## Scope-Skizze

1. Designfrage entscheiden (siehe oben).
2. `DdlGenerationOptions.includeComments: Boolean = true` ergänzen.
3. `AbstractDdlGenerator.generate()`: `generateHeader()`-Aufruf hinter
   `if (options.includeComments)`.
4. `DdlConfig`/`DdlConfigResolver`: `include_comments` als Top-Level-Schlüssel
   lesen (nicht dialekt-geschachtelt, wie `inline_foreign_keys`).
5. Falls Weg 1: CLI-Flag-Paar + Präzedenzlogik; falls Weg 2: kein CLI-Flag,
   nur Config → Default.
6. Handbuch: Abschnitt zu `schema generate`-Optionen ergänzen.

## Akzeptanzkriterien

- `ddl.include_comments: false` in der Konfigurationsdatei lässt
  `schema generate` ohne den `-- Generated by …`-Block laufen, für alle
  fünf Dialekte.
- Ohne den Schlüssel: unverändertes Verhalten (Header steht, wie heute).
- Golden-Master-Tests bleiben unberührt (Default bleibt `true`).

## Closure (2026-09-13)

Weg 2 umgesetzt (kein CLI-Flag, nur Config → Default), wie empfohlen — spart
die Boolean-Tri-State-Loesung, die sonst als erstes Vorbild fuer kuenftige
Boolean-Config-Schluessel gegolten haette.

**Umgesetzt:**

- `DdlGenerationOptions.includeComments: Boolean = true`.
- `AbstractDdlGenerator.generate()`: `generateHeader()`-Aufruf hinter
  `if (options.includeComments)`.
- `DdlConfigResolver`: neuer `readBoolean`-Helfer (SnakeYAML liest
  `true`/`false` bereits als `kotlin.Boolean`; alles andere bricht ab statt
  still auf den Default zu fallen), `ddl.include_comments` als
  Top-Level-Schluessel (nicht dialekt-geschachtelt, wie
  `inline_foreign_keys`).
- `SchemaGenerateWiring`/`SchemaGenerateRunner`: `includeComments` von der
  Config bis in `DdlGenerationOptions` durchgereicht — kein CLI-Flag, also
  kein neues Feld auf `SchemaGenerateOptions`/`SchemaGenerateCommand`.
- `spec/ddl-generation-rules.md` §1.2 (normative Stelle fuer den Header)
  ergaenzt statt `spec/cli-spec.md` — passend zu `ddl.mysql.engine` &Co.,
  die dort ebenfalls nicht als CLI-Flag-Zeile stehen.

**Bewusst nicht ergaenzt:** ein eigener Anwenderhandbuch-Abschnitt (anders
als im urspruenglichen Scope skizziert). Gemessen an `ddl.mysql.engine`/
`charset`/`collation` — denselben reinen Ziel-Beschreibungs-Schluesseln ohne
CLI-Gegenstueck — hat keiner von ihnen eine eigene Anwenderhandbuch-Stelle;
nur CLI-Flags bekommen dort Hinweise. `include_comments` bricht dieses
Muster nicht.

**Verifiziert:** `AbstractDdlGeneratorTest` (Header da/weg, beide Faelle),
`DdlConfigResolverTest` (Lesen, Typfehler, Praezedenz), `SchemaGenerateWiringTest`
(Config-Wert erreicht `DdlGenerationOptions`, Default ohne Config bleibt
`true`). Zwei Sabotagen durchgefuehrt und zurueckgenommen (Guard in
`AbstractDdlGenerator` und Resolver-Aufruf in der Wiring je einmal
neutralisiert, beide Male brach der jeweilige Test).
