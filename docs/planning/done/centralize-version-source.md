**Status**: Done — implementiert 2026-06-03 (open → done in einem
Schritt, weil der Refactor in einer Sitzung machbar war).

Implementierung:

- `dmigrate-version.properties` von
  `adapters/driving/cli/src/main/resources/` nach
  `hexagon/core/src/main/resources/` verschoben (Resource +
  `processResources`-Filter-Block wandern gemeinsam mit dem Loader).
- `dev.dmigrate.core.version.VersionInfo` (Singleton, lazy)
  liest die Resource via Classloader, mit
  `unknown`-Fallback + Placeholder-Detection (`$`, `{`, `}`),
  exakt wie der frühere `Main.cliVersion()`.

  `AbstractDdlGenerator.getVersion()`,
  `SchemaGenerateHelpers.formatJsonOutput` (`generator`-Feld),
  `TransformationReportWriter.render` (YAML `generator`-Feld),
  `NoOpAiProvider.DEFAULT_MODEL_VERSION`.

  `= VersionInfo.PRODUCT_VERSION` erhalten — CLI-Testoberfläche
  unverändert, aber Lade-Logik lebt nur einmal.
- Acht Produktiv-Output-Tests (`AbstractDdlGeneratorTest`,
  `SchemaGenerateHelpersTest`, `SchemaGenerateRunnerErrorTest`,
  `TransformationReportWriterTest` 2×, `CliGenerateTestPart2` 3×)
  asserieren jetzt gegen `VersionInfo.PRODUCT_VERSION` statt das
  Literal.
- `docs/user/releasing.md` §3 + §4.1 + §6 Checkliste auf die
  einzige Versions-Quelle `build.gradle.kts` /
  `defaultProjectVersion` reduziert.

§4 unten):

- 4× MCP-IT `clientInfo.version` (`McpAi*IT`, `McpHttp*IT`,
  `McpStdio*IT`) — Test-Client-Identität, nicht d-migrate-Version.
- 7× MCP-Test `modelVersion = "0.9.7"` (Handler/Resource/Store-
  Fixtures) — AI-Metadata-Fixture, nicht release-coupled.
- 2× CLI Lock-Payload-Tests (`McpStateDirLockTest`,

Ein Wert lebt in `build.gradle.kts` als
`defaultProjectVersion`-Konstante (überschreibbar via
`-PreleaseVersion` / `DMIGRATE_VERSION`-Env). Der Main-CLI-Pfad
nutzt diese Quelle bereits zur Build-Zeit über
`dmigrate-version.properties` (siehe
[`docs/user/releasing.md`](../../user/releasing.md) §4.1-Hinweis).
Aber `AbstractDdlGenerator.getVersion()` und die zwei Produktions-
Writer (`SchemaGenerateHelpers`, `TransformationReportWriter`) und
`NoOpAiProvider.DEFAULT_MODEL_VERSION` ignorieren diese Quelle.

**Aktivierungsbedingung**: Trigger feuert mit dem nächsten Release
(0.9.8 oder 1.0.0) — sobald ein weiterer Versions-Bump bevorsteht,
ist die zentrale Quelle die Voraussetzung, um nicht erneut zehn
Test-Dateien per `sed` nachzuziehen.

## Skizze einer Lösung

1. Ein `VersionInfo`-Singleton in `hexagon:core` oder
   `hexagon:ports-common`, das die Version aus
   `dmigrate-version.properties` (Resource im Classpath) liest. Eine
   einzige Konstante (`VersionInfo.PRODUCT_VERSION: String`) ist die
   neue Single-Source-of-Truth.

2. `AbstractDdlGenerator.getVersion()`, `SchemaGenerateHelpers`-JSON,
   `TransformationReportWriter`-YAML, `NoOpAiProvider.DEFAULT_MODEL_VERSION`
   ziehen aus `VersionInfo.PRODUCT_VERSION`.

3. Tests, die den Generator-Output verifizieren, asserten gegen
   `VersionInfo.PRODUCT_VERSION` statt ein Literal. So bleibt der
   Test stabil über Releases hinweg.

4. MCP-Tests, die `clientInfo.version` simulieren, sind ein
   **separater Fall**: das Literal identifiziert den Test-Client
   (`g9-it`, `g9-http-it` etc.), nicht den d-migrate-Server. Diese
   Strings können bei einem zentralen Versions-Refactor stabil
   bleiben oder explizit als „nicht release-coupled" markiert
   werden.

5. Golden-Master-SQL-Header: zwei Strategien möglich —
   a) Golden-Master-Vergleich strippt die Versions-Zeile vor
      Vergleich (vermutlich heute schon der Fall, da
      `minimal.postgresql.sql` mit `0.9.5` durchgeht trotz aktueller
      Release-Version), oder
   b) Golden-Master werden mit jeder Release-Tranche aktualisiert.
   Wenn Strategie (a) gilt, ist das `0.9.7` im Hotfix kosmetisch.
   Wenn (b), braucht es einen `make golden-update`-Schritt im
   Release-Ablauf.
